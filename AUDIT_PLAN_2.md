# План исправлений по итогам второго аудита

Второй аудит: код, механика игры, данные, синхронизация, производительность, UI/UX.
Пункты первого аудита (`AUDIT_PLAN.md`, этапы 1–11) закрыты и здесь не повторяются.

Обозначения пунктов — как в отчёте аудита: **H** — High, **M** — Medium, **L** — Low.
Critical-проблем не найдено.

**Статус:** план составлен и сверен с кодом, открытые решения приняты; работа не начата.

## Порядок работы на каждом этапе

1. Работа в отдельной ветке, `main` не трогаем.
2. Только правки текущего этапа — ничего сверх.
3. Сборка и тесты (`xcodebuild build` / `test`) — на Mac: в облачной среде Xcode нет.
4. Сводка: что изменено и почему, затронутые файлы, что проверить в симуляторе.
5. Коммит — только после одобрения.
6. **`push` — только по отдельной явной команде.**

Решения по этапам 4, 6 и 7 приняты (таблица «Открытые решения»), эти этапы можно начинать.

## Этап 1. Быстрые исправления механики (решений не требует)

- [ ] **H1** — экзамен всегда собирается из одних и тех же вопросов: `prefix(count)` берётся до перемешивания, поэтому «Пересдать» даёт тот же набор. Перемешивать до отбора — в обеих ветках (`examQuestions` и запасной `allQuestions`). Тест без случайности: генератор случайных чисел передаётся в use case (фиксированный seed), либо проверяется, что выборка — не первые N вопросов файла.
  `ExamUseCase.swift:162–166`
- [ ] **H5** — неверный индекс правильного ответа «зажимается» до последнего варианта, и правильным становится другой ответ. Такой вопрос отбрасывать — в том числе когда правильный ответ после обрезки пробелов оказался пустым; тест на путь загрузки, а не только на валидатор.
  `RemoteQuestion.swift:69, 83`
- [ ] **M3** — пауза в течение 1,5 с после ответа: автопереход не отменяется, таймер следующего вопроса идёт под экраном паузы. Кнопка «Пауза» недоступна, пока показывается результат ответа (вариант с отменой перехода не берём: после продолжения пришлось бы переходить к следующему вопросу, иначе таймер перезапустится на уже отвеченном); тест.
  `ExamViewModel.swift:229–236, 280–286`, `ExamView.swift:198–206`
- [ ] **M2** — «Сбросить достижения» обнуляет `totalQuestionsStudied`, но не `correctAnswers`: у гостя точность больше 100%. Сброс достижений не должен трогать статистику ответов.
  `StatsManager.swift:215–224`, `ProfileStatsSectionView.swift:83–84`
- [ ] **L1** — досрочное завершение повторения ошибок: процент считается с неотвеченными вопросами.
  `QuizViewModel.swift:426–430`
- [ ] **L2** — `QuizResult.isNewRecord` сравнивает с 0.8 вместо 80 (не используется — удалить).
  `Question.swift:83`
- [ ] **L3** — «мемоизация» в `@Observable` меняет состояние внутри геттера. Убрать.
  `QuizViewModel.swift:45–76`
- [ ] **L4** — NaN в `averageScore`, если первый экзамен завершён без ответов; статистика молча не сохраняется.
  `ExamMode.swift:214`
- [ ] Повторяющаяся строка генерации рекомендаций.
  `AdaptiveLearningEngine.swift:82–83`

## Этап 2. Защита сохранённых данных

Делается до любых изменений моделей (этапы 6–7).

- [ ] **H2** — у `UserStats`, `DailyProgress`, `ReviewSchedule`, `ExamStatistics`, `AppSettings`, `CodableAchievement` синтезированный `Decodable`: новое поле в модели → старые данные не читаются → `try?` подставляет пустую модель → первое сохранение стирает данные. Перейти на `decodeIfPresent` со значениями по умолчанию (как у `ProfileProgress`).
  `UserStats.swift:23`, `StatsManager.swift:35–37, 48–51`, `ExamUseCase.swift:212–218`, `AppSettings.swift`, `AchievementManager.swift:324–330`
- [ ] **H2** — то же для вложенных и облачных типов: `TopicStat`, `DifficultyStat`, `QuizResultRecord` (`UserStats.swift`); `UserProfile`, `ProfilePreferences`, `DifficultyPerformance`, `TopicProgress`, `LearningRecommendation`, `QuizHistoryEntry`, `ExamHistoryEntry`, `ExamConfigurationSnapshot` (`UserProfile.swift`). `UserProfile` — это и полезная нагрузка записи в iCloud: ошибка чтения в одном вложенном типе теряет весь профиль.
- [ ] **H2** — перечисления (`MasteryLevel`, `Difficulty` и др.): неизвестное значение не должно ломать чтение всего объекта — значение по умолчанию при неизвестном `rawValue`.
- [ ] Тесты: JSON без новых полей, JSON с неизвестным значением перечисления и JSON текущей версии читаются без потерь.
- [ ] При ошибке чтения не перезаписывать сохранённые данные пустыми (логировать и оставлять исходный ключ). В частности, `StatsManager.init` сразу вызывает `saveReviewSchedule()` — при неудачном чтении расписание тут же затирается.
  `StatsManager.swift:35–42`

## Этап 2b. Срочные исправления синхронизации (решений не требует)

Часть **H3**, которая портит данные вошедших пользователей при каждом запуске. Делается до этапа 6, не меняя архитектуру.

- [ ] Стабильный `id` у записей истории викторин: `rebuildProgressFromLocalStats` при каждом вызове создаёт `QuizHistoryEntry` с новым `UUID()`, `mergeQuizHistory` объединяет по `id` → история заполняется дублями. Хранить `id` в `QuizResultRecord` (через `decodeIfPresent`, этап 2) или выводить его из даты.
  `ProfileProgressBuilder.swift:66–76`, `ProfileMergeService.swift:155–165`
- [ ] `totalQuizzesCompleted` не брать из `quizHistory.count` (≤ 20) — синхронизировать сам счётчик в `ProfileProgress`.
  `StatsManager.swift:275`, `ProfileProgressBuilder.swift`

  `ProfileMergeService.swift:70–88`
- [ ] Тесты: повторная пересборка и слияние не создают дублей; счётчик викторин не обрезается после входа.

- [ ] **M10** (часть) — две модели статистики (`UserStats` и `ProfileProgress`) с синхронизацией в обе стороны → одна модель прогресса, синхронизируется полный снимок с правилами слияния для каждого поля.
